- (decision) Problem: before a new raid tier, guild must identify contested BiS items and which class/spec gains most from each; must be objective (sim-based), not guesswork
- (decision) Upgrade metric baseline = previous phase BiS; value = sim upgrade of new item vs prior-phase BiS for each spec
- (decision) Core output: table of contested items (BiS for 2+ classes) with ranked class priority; single-class BiS items are excluded
- (decision) Primary value: cut the time spent investigating a new phase's loot
- (assumption) User wants wowsims for sims and Wowhead loot tables via API or scraping only if permitted; research found Wowhead ToS forbids scraping and no public API - to confirm fallback to wowsims db.json
- (decision) Contested = item on the new phase BiS list of 2+ different specs (same class counts); only phase BiS items considered, not the full loot table
- (decision) Ranking metric = % DPS increase of new item vs spec's previous-phase BiS item (normalizes across specs with different DPS levels)
- (decision) Tanks out of scope: guild gives tanks loot priority by rule; healers and DPS do not compete for the same items
- (decision) v1 = generic per-spec BiS baseline; roster-specific (actual raider gear) is a possible later phase
- (decision) Healers in v1: healer-vs-healer contested items ranked by % HPS increase vs previous-phase BiS, accepting wowsims healer sims are alpha
- (decision) Loot table/item source = wowsims db.json (MIT) replacing Wowhead, whose ToS forbids scraping and which has no public API
- (decision) Stakes = internal, single guild use; target ~2-page PRD
- (assumption) Working mode not chosen by user; proceeding Fast path (draft with ASSUMPTION tags) given closed gaps and small stakes
- (event) Fast-path first draft written: 7 FRs across 4 features, 7 assumptions, 6 open questions
- (decision) Paired slots (rings/trinkets/1H) are simmed slot by slot, not as a pair; all combinations with the other slot's options are run
- (decision) Gems and enchants use wowsims defaults (not BiS-list gems)
- (decision) Tie-break: 1) higher % Upgrade Value; if tied, 2) higher absolute DPS/HPS gain; if still tied, 3) spec with higher theoretical DPS per Warcraft Logs data
- (decision) Output: CSV or HTML acceptable but must be functional - color coded, item links, drop source (boss/zone)
- (decision) Sim encounter: Patchwerk-style single target, 2-3 min fight; wowsims defaults acceptable
- (assumption) Warcraft Logs becomes a new data source for tie-break 3; API access/terms not yet researched
- (decision) Stakes refined: proof of concept for one guild; wowtbc.gg reuse permission deferred - owner: user, revisit if POC works
- (decision) Tie-break 3 uses Warcraft Logs top-percentile parse per spec as theoretical throughput
- (decision) Tie = Upgrade Values within the sim error margin
- (decision) Long runs acceptable; no cap on number of sims/combinations
- (decision) v1 targets TBC Anniversary; first Target Phase = P4 (ZA), Previous Phase = P3 (T6)
- (assumption) Target Phase parses do not exist pre-launch; tie-break 3 uses Previous Phase (or original TBC Classic era) top-percentile parses
